# Lesson 19 — Automated vs. Manual Lineage

**Chapter 4 · Documenting Lineage · Lesson 19 of 25**

## What you'll learn

- How manual lineage documentation is built, and why it's cheap to start but decays quickly
- How automated lineage is built, and what it actually scans to generate the graph
- The real trade-offs between the two approaches — automated isn't simply "better"
- Why most mature lineage practices end up using a hybrid of both

## Manual lineage

**Manual lineage** is documentation someone writes by hand: a diagram drawn in a tool, a wiki page describing a pipeline, a spreadsheet of source-to-target mappings. It's the fastest way to get started — no tooling investment, no scanning infrastructure, just someone who understands a pipeline writing down what they know.

The weakness is durability. The diagram is accurate the day it's drawn and reflects nothing automatically after that. Every schema change, every new pipeline, every decommissioned table requires someone to remember to go back and update the documentation — and in practice, that update is often the first thing skipped under deadline pressure. Manual lineage rots unless someone treats maintaining it as a standing responsibility, not a one-time task.

## Automated lineage

**Automated lineage** is generated by a tool that scans actual pipeline code, SQL queries, or query execution logs, and builds the dependency graph from what the code actually does, rather than from what someone remembers it does. A tool that parses SQL `SELECT` statements and `JOIN` clauses can infer that `FactTable` depends on `StagingView` without a human ever typing that relationship in.

This stays current almost by definition — re-run the scan after a code change, and the graph updates with it. The cost is tooling investment: picking, deploying, and maintaining a tool (Lesson 20 surveys real options), and accepting that automated scanning only sees what's expressed in code or logs it can parse.

## The real trade-off

Automated lineage's biggest blind spot is exactly what it can't see: a manual Excel export someone emails to a stakeholder, a one-off script run from someone's laptop, a copy-paste into another system — none of that shows up in a code scan, because none of it is code the tool can parse. These manual, undocumented hops are often where the most dangerous gaps live, precisely because nothing is watching them.

| | Manual | Automated |
|---|---|---|
| Setup cost | Low — just write it down | Higher — requires tooling |
| Stays current | No — decays without active upkeep | Yes — regenerates from the real pipeline |
| Covers undocumented steps | Yes, if someone knows about them | No — only sees what it can parse |

## The hybrid approach most organizations land on

In practice, most mature lineage practices use automated lineage as the backbone for anything that runs through parseable pipeline code, and manual documentation to fill the specific gaps automation can't reach — the Excel export, the legacy system nobody's rewritten, the tribal-knowledge step everyone just knows about. Lesson 21 picks this up directly: maintaining lineage over time is partly a tooling problem and partly a discipline problem, and neither approach solves the whole thing alone.

## Key terms

| Term | Meaning |
|---|---|
| Manual lineage | Lineage documentation written by hand, from a person's knowledge of the pipeline |
| Automated lineage | Lineage generated by a tool scanning actual code, queries, or execution logs |
| Blind spot | A dependency automated scanning cannot see because it isn't expressed in parseable code |
