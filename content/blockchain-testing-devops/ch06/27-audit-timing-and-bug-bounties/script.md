# Script — Audit Timing & Bug Bounties

## Segment 1 (title)

Lesson 26's checklist deliberately skipped one item. A security audit and a bug bounty both find bugs before they cause real damage, but they're not interchangeable, and they run on completely different clocks.

## Segment 2 (steps: audit vs bounty)

An audit is a fixed engagement -- a team of researchers reviews the code deeply for a set window, delivers a report, and it's over. A bug bounty is the opposite shape: an open-ended program that starts at launch and runs indefinitely, with no fixed end date.

## Segment 3 (screenshot: Code4rena audits board)

A competitive audit looks like this in practice -- a fixed submission window, a fixed prize pool, and multiple independent researchers all competing to find the same bugs in the same codebase before it ships. More eyes, same deadline.

## Segment 4 (screenshot: Immunefi bounty explorer)

Once live, a protocol is competing for researcher attention against every other bounty on the market -- 169 active programs here, ranked by vault size and maximum payout. A bounty that pays too little next to comparable protocols simply gets less serious attention.

## Segment 5 (screenshot: Immunefi severity payouts)

Payouts are scaled deliberately. A critical finding here pays up to a quarter million dollars -- calculated as a percentage of the funds actually at risk. That math is the whole point: make reporting a vulnerability more profitable than exploiting it.

## Segment 6 (outro)

An audit and a bounty both reduce risk, but neither reduces it to zero. Lesson 28 covers the next layer: phased rollouts and value caps, so a contract that's been audited and has an active bounty still launches with limits on how much it can actually lose.
