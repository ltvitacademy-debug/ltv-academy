# Lesson 12 — Implicit Sharing

**Chapter 2 · Advanced Sharing · Lesson 12 of 24**

## What you'll learn

- What implicit sharing is, and why it's not configured anywhere in Setup the way a sharing rule is
- The two directions implicit sharing runs: parent sharing and child sharing
- Why implicit sharing frequently grants more access than an admin consciously intended
- How "faster account sharing recalculation" changes the underlying mechanics without changing the visible behavior
- How to reason through an implicit-sharing scenario when a visibility question doesn't match any sharing rule you can find

## Access nobody configured

Every sharing mechanism covered so far — OWD, role hierarchy, sharing rules, manual sharing, Apex managed sharing, territories — is something an admin or developer deliberately set up. **Implicit sharing** is different: it's access the platform grants automatically based on object relationships, specifically between Account and its related Contacts, Opportunities, and Cases. Nobody checks a box to turn it on, and there is no dedicated Setup page listing "implicit shares" the way there's a page for sharing rules. It simply follows from how Account relates to its children, and an architect needs to be able to reason about it precisely because it's invisible in Setup but very visible in support tickets about "why can this person see that."

## Parent sharing: child access implies read-only parent access

The first direction is **parent sharing**: if a user has access to a child record (an Opportunity, Contact, or Case) through any mechanism — ownership, a sharing rule, a team, Apex managed sharing, anything — they automatically get **read-only** access to that child's parent Account, even if nothing explicitly shares the Account itself with them. This makes practical sense: a rep who was given access to one specific Opportunity needs to see basic facts about the Account it belongs to (industry, billing address, who else is involved) to work the deal, even if they have no business seeing the Account's other children. The access is capped at Read regardless of what level the user has on the child — it never grants Edit on the Account itself, and it is not treated as a sharing-rule grant that shows up as a configured rule anywhere.

## Child sharing: Account access can imply access to its children

The second direction is **child sharing**, and it runs the opposite way: access to an Account, combined with how the Account owner's role is configured for child-record access ("child access settings" — View or View and Edit options for the owner's role, configured on the role itself), can imply access down to the Account's related Contacts, Opportunities, and Cases. Account Teams interact with this directly — a user added to an Account Team can be granted access to the team member's related Opportunities, Cases, and Contacts as part of the team configuration, which is itself a form of child sharing riding on top of the Account relationship rather than a separate manual grant on each child record.

## Why this surprises people

Implicit sharing is the single most common reason a record-visibility investigation turns up more access than anyone can account for from sharing rules and role hierarchy alone. A classic scenario: a manager asks why a rep who was never added to a sharing rule, team, or role above the Account owner can still see an Opportunity. The answer is often that the rep has access to the parent Account through some other path (a different sharing rule entirely, or a role above the Account owner), and the Account owner's role has child access set to "View" for Opportunities — so access flows down implicitly, with no row in any sharing rule or team related list to point to. An architect auditing access (Chapter 4's topic) has to know to check implicit paths, not just the explicit grants, or the audit will under-report real access.

## A mechanical change, not a behavioral one: faster account sharing recalculation

Historically, implicit shares were materialized as actual rows in the Contact/Opportunity/Case share objects (`RowCause` of `Rule` or `Team`, generated by the platform) — meaning you could query them with SOQL like any other share row. Salesforce's **faster account sharing recalculation** improvement changes the underlying mechanism: once enabled, the platform stops storing persistent implicit share rows for these parent/child relationships and instead evaluates access dynamically at query time. The visible behavior for end users doesn't change — the same people can see the same records — but any Apex or test code that assumed it could query those implicit share rows directly will return nothing once this is on, which is exactly the kind of platform change that breaks a brittle integration test silently until someone traces a "missing" row back to this setting.

## Key terms

| Term | Meaning |
|---|---|
| Implicit sharing | Automatic, non-configured access the platform grants based on Account-to-child object relationships |
| Parent sharing | Access to a child record (Contact/Opportunity/Case) grants automatic read-only access to its parent Account |
| Child sharing | Access to an Account, combined with the owner's role child access settings, can imply access to its children |
| Child access settings | A role-level configuration (View / View and Edit) controlling whether role-based Account access extends to children |
| Faster account sharing recalculation | A platform change that evaluates implicit access dynamically instead of storing persistent implicit share rows |
