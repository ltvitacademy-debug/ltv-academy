# Reproducibility Across the Full ML Lifecycle

Versioning the data (Lesson 27) and versioning the model (Lesson 11) each solve one link in a chain, but neither alone answers the question that actually matters during an incident or an audit: given this exact deployed model, can you reproduce the exact training run that created it, byte for byte? That requires every link in the chain — data, code, environment, and parameters — to be captured together, not separately.

## What you'll learn

- The four things that must be captured together for a training run to be truly reproducible
- Why a `dvc.lock` file and a Git commit hash have to be read together, not separately
- How to capture the training environment, not just the code, with a lockfile and a container digest
- How MLflow's run tracking ties parameters, metrics, and environment to one run ID
- Why a reproducibility manifest is the artifact that actually answers "can we rebuild this"

## The four links in the chain

A training run is only reproducible if all four of these are pinned to a specific, retrievable version at the same time:

1. **Data** — which exact version of which dataset (a DVC hash, a Delta Lake `VERSION AS OF`)
2. **Code** — which exact commit trained it (a Git SHA)
3. **Environment** — which exact library versions and system dependencies ran it (a lockfile, a container image digest)
4. **Parameters** — which hyperparameters, random seeds, and config values were used

Missing any one of the four breaks the chain. A pinned Git commit with an unpinned `requirements.txt` (`scikit-learn>=1.3`) can silently produce a different model six months later when a new scikit-learn release changes a default.

## Linking data and code together

DVC's own lockfile, `dvc.lock`, records the exact hash of every dependency and output for every pipeline stage at the moment `dvc repro` ran — and because it's a plain file, it gets committed to Git alongside the code:

```yaml
stages:
  train:
    cmd: python train.py data/train.csv model.pkl
    deps:
      - path: data/train.csv
        md5: a1b2c3d4e5f6a7b8c9d0e1f2a3b4c5d6
      - path: train.py
        md5: f6e5d4c3b2a1908f7e6d5c4b3a2f1e0d
    outs:
      - path: model.pkl
        md5: 1a2b3c4d5e6f7a8b9c0d1e2f3a4b5c6d
```

Checking out a specific Git commit now gets you both the code *and* a lockfile pointing at the exact data version it ran against — `git checkout` plus `dvc checkout` together reconstruct the full input state.

## Pinning the environment, not just the code

A Git commit alone says nothing about which library versions actually ran. Two common ways to close that gap:

```text
# requirements.lock (generated by pip freeze / pip-compile)
scikit-learn==1.3.2
pandas==2.1.4
numpy==1.26.2
```

```bash
# the container digest, not just the tag
docker pull ml-training:latest
docker inspect --format='{{.RepoDigests}}' ml-training:latest
# -> ml-training@sha256:9f3b1c...
```

A tag like `ml-training:latest` is mutable — it can point at a different image tomorrow. The digest (`sha256:...`) is a content hash of the image itself, and it's the only thing that guarantees "this is the exact same container" months later.

## MLflow: tying it together under one run ID

MLflow's tracking API is built to capture several of these links under a single run, so they're never recorded separately in the first place:

```python
import mlflow

with mlflow.start_run() as run:
    mlflow.log_param("learning_rate", 0.01)
    mlflow.log_param("random_seed", 42)
    mlflow.set_tag("git_commit", "a1b2c3d")
    mlflow.set_tag("data_version", "dvc:a1b2c3d4e5f6")
    mlflow.sklearn.log_model(clf, "model")
```

The run ID becomes the single identifier that, read back later, tells you the parameters, the Git commit, and the data version together — exactly the information a reproducibility question needs, without hunting across three separate systems.

## The reproducibility manifest

Teams in regulated or high-stakes settings often go one step further and generate an explicit manifest alongside the model artifact, rather than relying on someone to manually correlate a Git log with an MLflow run:

```json
{
  "model_version": "fraud-detector-v3",
  "git_commit": "a1b2c3d",
  "data_version": "dvc:a1b2c3d4e5f6",
  "environment_digest": "sha256:9f3b1c...",
  "hyperparameters": { "learning_rate": 0.01, "random_seed": 42 },
  "trained_at": "2026-09-14T03:12:00Z"
}
```

This manifest is what Lesson 30's auditability requirements actually get checked against — it's the single file that answers "can we rebuild this" without anyone having to reconstruct the chain by hand.

## Key terms

| Term | Meaning |
|---|---|
| Reproducibility chain | Data, code, environment, and parameters, all pinned together |
| `dvc.lock` | Records exact hashes for every pipeline stage's dependencies and outputs |
| Container digest | A content hash of a container image, unlike a mutable tag |
| MLflow run ID | A single identifier tying parameters, tags, and model artifact together |
| Reproducibility manifest | An explicit record linking a model version to its full chain of inputs |

## Recap

True reproducibility requires pinning data, code, environment, and parameters together, not separately — a `dvc.lock` file ties data to code, a lockfile or container digest pins the environment, and MLflow's run tracking (or an explicit manifest) ties all of it to one retrievable identifier.
