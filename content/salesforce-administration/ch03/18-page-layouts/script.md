# Script — Page Layouts

## Segment 1 (title)

Chapter 2 covered the app someone works in and the navigation around it. This chapter goes one level deeper: the object itself, and how its fields, related lists, and buttons are arranged on the record a user actually edits. That foundation is the page layout.

## Segment 2 (screenshot: Case Page Layouts list)

Most objects ship with one default layout, but it's common for an object to have several. A support team might see a Problem layout built for root-cause analysis, while a sales team sees a Suggestion layout with a completely different set of fields — same Case object, six different layouts in this org.

## Segment 3 (screenshot: field column arrangement)

A page layout controls which fields appear, whether they're required, which related lists and buttons show up, and how fields are arranged — one column or two. Same fields, same record: two columns versus one stacked column changes how much scrolling a user does to see everything.

## Segment 4 (screenshot: Assign page layouts step)

A layout only matters once it's assigned. From Page Layout Assignment, an admin maps each record type and profile combination to a specific layout — one layout for every profile, or a different layout per profile.

## Segment 5 (steps: layouts vs. Lightning pages)

Page layouts are older and field-focused. Lightning record pages, from last lesson, are newer and component-focused — but in most orgs today, a Lightning record page's Record Detail component still pulls its fields straight from the assigned page layout underneath it.
