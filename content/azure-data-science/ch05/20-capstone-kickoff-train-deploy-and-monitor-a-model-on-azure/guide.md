# Capstone Kickoff: Train, Deploy and Monitor a Model on Azure

You have now seen every piece of the Azure data science stack: workspaces, compute, jobs, MLflow tracking, pipelines, the model registry, real-time and batch endpoints, monitoring and responsible AI tooling. The capstone ties them into one project you can put in a portfolio: take a business problem all the way from raw data to a monitored, documented model. This lesson is the kickoff. You will frame the problem, set success criteria *before* modeling, sketch the architecture, and build the baseline that every later step has to beat.

## What you'll learn

- How to turn a vague request into a testable project brief with success criteria

- Why you build a dumb baseline first, and what it looks like in numbers
- A repository layout that makes the project easy to review

## The brief

The scenario: a subscription business (call it Northwind Streams, illustrative) loses about a third of its customers over the period we measure, and the retention team can only phone so many people a week. They want a **churn risk score** for each customer, available two ways: instantly for the support screen (a real-time endpoint) and in bulk every night for the campaign list (a batch endpoint). They also want to be told when the model stops being trustworthy.

Notice what that sentence contains: a prediction target, two consumption patterns and a monitoring requirement. Before touching a model, write down what "done" means. For this project I set these targets, which are my choices for the exercise, not Azure requirements:

1. The model beats a naive baseline by a clear margin on held-out data, with ROC AUC of at least 0.75.
2. Recall is reported per contract type, not only overall, so weak segments are visible.
3. The model is packaged in MLflow format and scores a JSON request in the shape Azure ML endpoints expect.
4. A drift check compares production data with training data and flags large shifts.
5. A model card records data, metrics, limits and what the model must not be used for.

## The architecture

The path has six stages, each of which you already know:

1. **Data and baseline** (this lesson).
2. **Train and track** with MLflow, comparing several candidate runs.
3. **Register** the best model in the workspace registry.
4. **Deploy** to a managed online endpoint, and optionally a batch endpoint for the nightly list.
5. **Monitor** with data-drift signals and alerts.
6. **Review and present**: fairness and segment checks, model card, cleanup, portfolio write-up.

Because no Azure account is available in this course, everything that only exists in the cloud (registering in a workspace, creating endpoints, scheduling monitors) is shown as clearly labeled, illustrative code adapted from Microsoft Learn. Everything else runs on your laptop with scikit-learn, pandas and a local MLflow tracking folder. If you do have a subscription, you can point the same code at your workspace, and remember the cost rule for the whole project: a deployed online endpoint keeps compute running, so delete it when you finish.

## Build the baseline

The dataset is synthetic, generated by a small function with a fixed seed so results are reproducible. It has four features: `tenure_months`, `monthly_spend`, `support_tickets` and `contract`, plus the `churned` label.

```python
df = make_data()          # 5,000 synthetic customers
print(df.shape, "churn rate", round(df["churned"].mean(), 3))
print(df.head(3).to_string(index=False))
```

```
(5000, 5) churn rate 0.353
 tenure_months  monthly_spend  support_tickets       contract  churned
            25          69.68                3       one-year        0
            16          45.69                2 month-to-month        1
            37          66.60                0       two-year        0
```

With a 35% churn rate, a model that always predicts "won't churn" is 65% accurate while finding no churners at all. That is the **baseline**, and it is the reason accuracy is a poor headline metric here. I split 75/25 with stratification and evaluated two models on the held-out quarter:

```python
dummy = DummyClassifier(strategy="most_frequent").fit(Xtr, ytr)

pre = ColumnTransformer([
    ("num", StandardScaler(),
     ["tenure_months", "monthly_spend", "support_tickets"]),
    ("cat", OneHotEncoder(), ["contract"])])
pipe = Pipeline([("prep", pre),
                 ("clf", LogisticRegression(max_iter=1000))])
pipe.fit(Xtr, ytr)
```

What I measured:

```
baseline accuracy 0.647 AUC 0.5 recall 0.0
logreg AUC 0.793 recall@0.5 0.515 accuracy 0.737
```

The dummy model gets 0.647 accuracy, an AUC of exactly 0.5 and zero recall. The logistic regression pipeline reaches an AUC of 0.793 and finds about half the churners at the default 0.5 threshold. It clears success criterion 1. Notice that preprocessing (scaling and one-hot encoding) lives inside the pipeline. That matters later: when the whole pipeline is the model, an endpoint can accept raw columns and there is no risk of the training-time and serving-time transformations drifting apart.
