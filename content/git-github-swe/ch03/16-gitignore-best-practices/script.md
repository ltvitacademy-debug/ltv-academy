# Script — .gitignore Best Practices

## Segment 1 (title)

A .gitignore entry belongs to things that are regenerable, like dependencies and build output, or machine-specific, like editor settings — never source code the team needs to share.

## Segment 2 (code: four categories)

Dependencies are reinstallable from a lockfile. Build output gets regenerated by the build. Editor and OS noise is specific to one person's machine. Local config and secrets differ per environment and should never be shared.

## Segment 3 (code: patterns)

.gitignore supports wildcards and directories, not just exact filenames. A leading slash anchors a pattern to the repo root. A leading exclamation point negates a previous pattern, letting you re-include one file inside an otherwise ignored folder.

## Segment 4 (code: already-tracked files)

.gitignore only affects files Git isn't already tracking. Add a pattern for a file you already committed, and Git keeps tracking it anyway — you have to untrack it first with git rm cached.

## Segment 5 (steps: what it can't undo)

If a secret was committed before it was ever added to .gitignore, it's still sitting in history, in every clone and fork, recoverable forever. The fix isn't just adding it to .gitignore after the fact — it's getting .env and credential files ignored before the very first commit, and rotating any key that already leaked.
