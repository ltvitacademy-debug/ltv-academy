## What .gitignore actually controls

`.gitignore` is a plain text file, one pattern per line, telling Git
which untracked files to leave out of `git status` and `git add .`
entirely. It has one hard limit worth knowing up front: it only
affects files Git **isn't already tracking**. Add a pattern for a
file you already committed, and Git keeps tracking it — ignoring a
tracked file requires removing it from tracking first:

```
$ git rm --cached config/secrets.yml
$ echo "config/secrets.yml" >> .gitignore
$ git commit -m "Stop tracking secrets.yml, add to .gitignore"
```

## What belongs in almost every .gitignore

Four categories cover most of what any project should ignore:

```
# Dependencies — reinstallable from a lockfile, don't belong in history
node_modules/
vendor/
__pycache__/

# Build output — regenerated by the build, not source
dist/
build/
*.pyc

# Editor/OS noise — specific to one person's machine
.vscode/
.DS_Store
Thumbs.db

# Local config & secrets — differs per environment, never shared
.env
.env.local
*.pem
```

The principle underneath all four: a `.gitignore` entry belongs to
things that are either **regenerable** (dependencies, build output) or
**machine/person-specific** (editor settings, local secrets) — never
source code or anything the team needs to share.

## Patterns, not just filenames

`.gitignore` supports wildcards and directory matching, which is what
makes short rules cover a lot of ground:

```
*.log            # any file ending in .log, anywhere
/build            # only a top-level build/, not src/build/
logs/             # any directory named logs, at any depth
!important.log    # exception — re-include this one file
```

A leading `/` anchors a pattern to the repository root; without it,
the pattern matches at any depth. A trailing `/` means "directories
only." A leading `!` negates a previous pattern — useful for ignoring
a whole directory except one file you do want tracked.

## GitHub's own starting point

Writing a `.gitignore` from scratch for every new project stack is
unnecessary — GitHub maintains a library of language- and
framework-specific templates (Node, Python, Java, and dozens more) at
[github.com/github/gitignore](https://github.com/github/gitignore),
and the "Add .gitignore" step is built directly into GitHub's own
"create a new repository" flow, pre-filling a sane starting set for
whatever stack you pick.

## Global ignores, for machine-specific noise

Some ignore patterns — your editor's folder, your OS's thumbnail
cache — have nothing to do with any particular project and shouldn't
be committed to every repository's `.gitignore` individually. Git
supports a **global** ignore file for exactly this:

```
$ git config --global core.excludesfile ~/.gitignore_global
$ echo ".DS_Store" >> ~/.gitignore_global
$ echo ".vscode/" >> ~/.gitignore_global
```

## The one thing .gitignore can't do

`.gitignore` only prevents *future* commits of a file — it does
nothing for a secret that's already in the repository's history. If
an API key was committed before it was added to `.gitignore`, it's
still sitting in every clone and every fork's history, recoverable
with `git log -p`, forever, until the history itself is rewritten
(a separate, more invasive operation) and the key is rotated. The
real lesson: get `.env` and credential files into `.gitignore`
*before* the first commit of a new project, not after.

## Key terms

| Term | Meaning |
|---|---|
| `.gitignore` | A file listing patterns of untracked files Git should never stage automatically |
| `git rm --cached` | Stops tracking a file without deleting it from disk — required before ignoring an already-committed file |
| Global ignore file | A `.gitignore`-style file applied across every repository on your machine, for editor/OS noise |
| `github/gitignore` | GitHub's maintained library of starter `.gitignore` templates by language and framework |
