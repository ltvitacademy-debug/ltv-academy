# Lesson 27 — Surrogate Keys in Snowflake

**Chapter 6 · Data Warehousing & Dimensional Modeling in Snowflake · Lesson 27 of 60**

## What you'll learn

- `AUTOINCREMENT` / `IDENTITY` column syntax — Snowflake's equivalent of T-SQL's `IDENTITY`
- Why Snowflake's version doesn't guarantee gap-free, strictly sequential values the way you might expect
- The `HASH()`-based surrogate key pattern common in Snowflake ELT, and why it exists
- When to reach for each

## AUTOINCREMENT / IDENTITY: the syntax you'd expect

Snowflake supports the same idea as T-SQL's `IDENTITY` column, with
two interchangeable spellings:

```sql
CREATE TABLE analytics.dim_customer (
    customer_key  NUMBER AUTOINCREMENT START 1 INCREMENT 1,
    customer_id   VARCHAR NOT NULL,
    customer_name VARCHAR
);

-- Identical meaning, T-SQL-flavored spelling:
CREATE TABLE analytics.dim_product (
    product_key NUMBER IDENTITY(1,1),
    product_id  VARCHAR NOT NULL
);
```

Insert without naming the key column, and Snowflake assigns the next
value automatically — same experience as T-SQL.

## The catch: not strictly sequential or gap-free

In T-SQL, you already know `IDENTITY` values can have gaps (a failed
transaction still consumes a value). Snowflake's `AUTOINCREMENT` has
the same caveat, more pronounced: Snowflake loads data in parallel
across many micro-partitions, so values generated by concurrent
inserts are **not guaranteed to be gap-free or assigned in insertion
order**. That's fine for a key's actual job — being unique and stable
— but don't build logic that depends on customer_key 105 having been
inserted before customer_key 106.

## The HASH()-based pattern common in Snowflake ELT

A different, genuinely Snowflake-idiomatic pattern shows up constantly
in real ELT code: generating the surrogate key *deterministically*
from the natural key, using `HASH()`, right inside the transformation
that builds the dimension:

```sql
CREATE OR REPLACE TABLE analytics.dim_customer AS
SELECT
    HASH(customer_id) AS customer_key,
    customer_id,
    customer_name,
    region
FROM staging.customers_cleaned;
```

Why this pattern exists, when `AUTOINCREMENT` already works:

- **No round trip needed.** A staging transformation that needs to
  reference a dimension's surrogate key (say, when building the fact
  table in the same pipeline run) can compute `HASH(customer_id)`
  independently, without first inserting into the dimension and
  reading the assigned key back.
- **Deterministic across reruns.** The same natural key always
  produces the same surrogate key, every run, on every table that
  computes it — useful when a fact table and a dimension table are
  built by separate, independently-scheduled transformations that
  still need to agree on the key.
- **Fits `CREATE OR REPLACE TABLE ... AS SELECT`.** Lesson 22's
  idempotent rebuild pattern doesn't preserve `AUTOINCREMENT` state
  cleanly across a full rebuild — a `HASH()`-based key sidesteps that
  entirely, since it's recomputed identically every time.

## When to reach for each

| | `AUTOINCREMENT` / `IDENTITY` | `HASH()`-based |
|---|---|---|
| Feels like | T-SQL, familiar | Snowflake ELT-idiomatic |
| Needs the dimension row to exist first | Yes | No — computable independently |
| Survives `CREATE OR REPLACE TABLE AS SELECT` rebuilds cleanly | Not automatically | Yes, by construction |
| Best fit | Tables loaded by simple, sequential `INSERT` | Tables built by CTAS-based ELT pipelines |

## Key terms

| Term | Meaning |
|---|---|
| `AUTOINCREMENT` / `IDENTITY` | Snowflake's auto-generated sequential key column — same idea as T-SQL |
| Natural key | The business-meaningful identifier from the source system (e.g., `customer_id`) |
| `HASH()` | A deterministic function producing the same output for the same input — used to derive a surrogate key without a round trip |
