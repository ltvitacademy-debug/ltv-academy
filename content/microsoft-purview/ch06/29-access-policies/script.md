# Lesson 29 — Access Policies · Voiceover script

Segments map 1:1 to slides. Target: ~2-3 minutes total.

---

## S1 · TITLE CARD

Lesson 28 covered how a governance team writes a policy. This lesson follows the other half: what a data consumer actually sees when they want access to something they found in the catalog.

## S2 · SCREENSHOT (search or browse)

It starts exactly where discovery always starts — the catalog search bar, or Browse assets by source and collection.

## S3 · SCREENSHOT (request access button)

On the asset's own page, Request access sits right in the same menu as Edit and Delete — not buried in a separate ticketing system the consumer has to go find.

## S4 · SCREENSHOT (send)

A short justification, an optional box to request on someone else's behalf, then Send — the action that actually fires the workflow and notifies the approver.

## S5 · SCREENSHOT (resulting record)

Once approved, the request doesn't just vanish — it becomes a tracked record: data source path, access type, requestor, and a date. An audit trail, not a one-time favor.

## S6 · STEPS CARD (statuses)

Every request moves through the same states, in order: Pending while it waits for a decision, Approved once granted but not yet provisioned, and Completed once the consumer can actually use the data.

## S7 · OUTRO CARD

Access answers who can see the data. Next, Data Quality in Purview asks a different question: once someone has access, can they actually trust what they're looking at?
