# Versioning Stored Procedures & Views

Once you've decided database objects belong in Git, the next practical question is
structural: do you commit one enormous file with the entire schema, or break it apart? The
real-world answer, and the one database projects are built around, is one file per object —
and the reason is almost entirely about what a Git diff actually looks like.

## What you'll learn

- The one-object-per-file convention, and what it looks like on disk
- Why a single giant schema-dump file makes Git diffs unreadable
- What a real diff on a single stored procedure file looks like, and why that's the point

## One file, one object

The practice that database projects (Lesson 13) formalize, and that you should follow even
without one, is simple: each stored procedure, view, function, or table gets its own
`.sql` file containing the full `CREATE` (or `CREATE OR ALTER`) script for that single
object.

```text
sql/
├── Tables/
│   └── Orders.sql
├── Views/
│   └── vw_OrderSummary.sql
└── StoredProcedures/
    ├── usp_GetOrderTotals.sql
    └── usp_CancelOrder.sql
```

`usp_GetOrderTotals.sql` contains nothing but the full script to create
`usp_GetOrderTotals`. Nothing else. When that procedure changes, that's the only file that
changes.

## Why a single dump file breaks the workflow

The alternative — one giant `.sql` file with the entire database's schema, generated by a
"script out the whole database" export — seems simpler at first, but it destroys the value
Git is supposed to provide. Change one line in one stored procedure buried three thousand
lines into a ten-thousand-line file, and the pull request diff is a needle in a haystack:
reviewers have to scroll past everything else to find the one real change, and worse, two
people who each modify a *different* unrelated object on the same day frequently produce a
merge conflict in the same giant file, even though their actual changes never touch the same
object at all.

## What a real diff looks like

With one file per object, a change to `usp_GetOrderTotals` produces a diff that shows
exactly, and only, what changed in that procedure:

```diff
 CREATE OR ALTER PROCEDURE usp_GetOrderTotals
     @IncludeTax BIT = 0
 AS
 BEGIN
-    SELECT OrderId, SUM(LineTotal) AS Total
+    SELECT OrderId,
+           SUM(LineTotal) * CASE WHEN @IncludeTax = 1 THEN 1.08 ELSE 1 END AS Total
     FROM OrderLines
     GROUP BY OrderId
 END
```

A reviewer looking at this pull request sees exactly one procedure changed, exactly what
changed inside it, and nothing else — which is the entire point of code review working at
all. Two developers changing `usp_CancelOrder` and `vw_OrderSummary` on the same day never
conflict with each other, because they're editing entirely different files.

## Key terms

| Term | Meaning |
|---|---|
| One-object-per-file | The convention of giving each database object its own `.sql` file containing its full CREATE script |
| `CREATE OR ALTER` | A T-SQL form that creates an object if it doesn't exist, or alters it in place if it does — common in versioned object scripts |
| Diff | The line-by-line comparison Git shows between two versions of a file |
| Merge conflict | What happens when two changes touch the same lines of the same file and Git can't automatically reconcile them |

## Check yourself

Two developers each change a different stored procedure in the same sprint, and both submit

with each other in Git — and what would happen instead if the whole schema lived in one
file?
