# Lesson 11 — Multi-Factor Authentication

**Chapter 2 · Enterprise Identity · Lesson 11 of 24**

## What you'll learn

- Why Salesforce made MFA mandatory for direct UI logins rather than optional

- How Session Security Levels connect MFA to specific actions, not just login
- How MFA interacts with SSO — a frequently misunderstood architectural point

## Why MFA became mandatory

Passwords alone are a weak authentication factor: they get reused across sites, phished, and leaked in breaches of completely unrelated services. Salesforce's response was to make MFA a baseline login requirement for every org's direct UI logins (username/password-based access), not an optional feature admins might or might not turn on. The reasoning connects directly back to Lesson 1's three-factor model — requiring a password (something you know) plus a second, independent factor (something you have, like a mobile authenticator app, or something you are) makes credential-stuffing and phishing attacks dramatically less effective, because stealing a password alone no longer grants access.

## Verification methods Salesforce supports

Salesforce supports several MFA verification methods, with varying strength and user experience trade-offs:

- **Salesforce Authenticator** (Salesforce's own mobile app) — push-based approval, can include location-based automated approval for trusted locations.
- **Third-party authenticator apps** generating time-based one-time passwords (TOTP) — Google Authenticator, Microsoft Authenticator, and similar apps.
- **Security keys** (WebAuthn/U2F hardware keys, or built-in biometric authenticators like Windows Hello or Touch ID) — generally the strongest option, resistant to phishing because the cryptographic challenge is tied to the specific site.
- **Built-in authenticators** on the user's device, using platform biometrics.

Notably, SMS text and email one-time codes have been phased down by Salesforce as a primary MFA method in favor of app-based or hardware-based verification, reflecting the broader security industry's move away from SMS-based codes, which are vulnerable to SIM-swapping attacks.

## Session Security Levels: MFA tied to specific actions

MFA isn't only a login-time gate. Lesson 1 introduced **Session Security Levels** (Standard vs. High Assurance), configured on the **Session Settings** page. This lets an admin require a stronger authentication event before a user can perform a specific sensitive action — viewing a report containing personal data, exporting records in bulk, or changing their own MFA settings — even if their original login only needed Standard-level authentication.

Checking that **Multi-Factor Authentication** sits in the **High Assurance** column on Session Settings is a well-known Trailhead and real-world "don't skip this" step: if it's missing from High Assurance, actions that are supposed to require strong authentication may not actually enforce it, silently weakening the control an admin thinks is in place.

## MFA and SSO: a common point of confusion

A frequent misunderstanding: "we use SSO, so we don't need Salesforce MFA." This is backwards. If a user authenticates via SP-initiated SSO (Lesson 10), Salesforce's *own* MFA requirement doesn't apply to that login event — but that only works because the burden of strong authentication has shifted to the external IdP. The external IdP, not Salesforce, now has to be the one enforcing MFA. An architect reviewing an SSO rollout has to explicitly verify that the external IdP enforces MFA (or an equivalent strong authentication policy) — assuming SSO alone satisfies a client's security or compliance requirement for multi-factor authentication, without checking the IdP side, is a design error that shows up in real security audits.

## Key terms

| Term | Meaning |
|---|---|
| Multi-Factor Authentication (MFA) | Authentication requiring two or more independent factors |
| TOTP | Time-based one-time password, generated by an authenticator app |
| Security key | A hardware or platform authenticator using WebAuthn/U2F, resistant to phishing |
| Session Security Level | Standard vs. High Assurance classification tied to how strongly a session was authenticated |
| High Assurance | The session security tier that should include Multi-Factor Authentication |
