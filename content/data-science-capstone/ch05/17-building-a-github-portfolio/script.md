# Script — Building a GitHub Portfolio

## Segment 1 (title)

Your resume makes a claim. Your GitHub is where a reviewer can check it. Many hiring managers will spend about two minutes on the README of your best project, so this lesson is about making those two minutes count, and avoiding the mistakes that quietly sink a portfolio.

## Segment 2 (steps: what reviewers see)

Reviewers are busy. Commonly they look at your pinned repositories first, then the README, then the layout, and only then maybe a notebook. So pin your best three or four projects. Three clear projects usually beat twenty half-finished ones.

## Segment 3 (code: README skeleton)

A good README answers four questions in order. What was the problem? What did you do? What did you find? And how can I run it? Put a one-paragraph business summary and your headline result at the top, add a chart, and include a short section on limits and next steps.

## Segment 4 (code: repo layout)

Keep the layout simple. A README, a requirements file, a gitignore, then folders for sql, notebooks, source code and reports. Number your notebooks, pin library versions, and set random seeds, so a stranger can rerun your results.

## Segment 5 (steps: safety checklist)

Before you go public, run a checklist. No secrets: no passwords, keys or tokens, in code or notebooks. Data rights: only publish data you may share, and cite sources. Synthetic disclosure: say plainly that the capstone data is fictional. And review notebook outputs for anything private.

## Segment 6 (code: gitignore)

Here's a starter gitignore. If you ever commit a secret, deleting it later is not enough, because it stays in the history. Revoke or rotate that key and treat it as compromised.
