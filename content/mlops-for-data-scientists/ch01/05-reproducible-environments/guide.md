# Reproducible Environments

Your code is in Git, and your settings are in `params.yaml`. There is one more input to every training run that neither of them records: the **environment**, meaning the Python version and every library installed next to your code. A model is produced by code, data, settings and the libraries that run them. Change any one and the result can change. This lesson makes the environment something you write down, rebuild on demand and check, using the `churn-project` from lessons 3 and 4. Everything below was run for real on Python 3.9 in scratch folders outside the course repo.

## What you'll learn

- Why an unpinned `requirements.txt` breaks over time, with a real failure
- How to create an isolated virtual environment for one project
- The difference between a requirements file and a lock file
- How to rebuild an environment from scratch and prove it matches
- What can go wrong when a saved model meets a different library version

## Isolate with a virtual environment

A virtual environment is a private folder of packages for one project, so that two projects never fight over versions. From the project root:

```
python -m venv .venv
.venv\Scripts\activate          # Windows
source .venv/bin/activate       # macOS / Linux
pip install -r requirements.txt
```

`.venv/` is machine-specific and large, so it goes in `.gitignore` (lesson 4 already ignored it). Everyone rebuilds it from the requirements file.

## The trap: pinning only some libraries

Our `requirements.txt` from lesson 3 lists four direct dependencies, all pinned to exact versions:

```
scikit-learn==1.1.2
pandas==1.4.3
joblib==1.1.0
pyyaml==6.0.3
```

We built a fresh virtual environment from it and ran training. It failed:

```
$ python -m churn.train
ValueError: numpy.dtype size changed, may indicate binary incompatibility.
Expected 96 from C header, got 88 from PyObject
$ pip freeze | grep numpy
numpy==2.0.2
```

NumPy is not in our file at all. scikit-learn and pandas only declare a *minimum* NumPy version, so pip installed the newest release, and that release is too new for the compiled pandas code we pinned. Worse, `pip check` reported "No broken requirements found", because the declared version ranges were satisfied. The lesson is that **pinning what you import is not enough; you must pin the libraries your libraries install** (the transitive dependencies).

## Requirements file vs. lock file

Keep two files with two jobs:

- **`requirements.txt`** lists the libraries you chose, the short human-readable list. Some teams keep ranges here (`pandas>=1.4,<2`).
- **`requirements.lock`** lists every installed package with an exact version, generated by a tool, never edited by hand.

We fixed the environment by adding `numpy==1.23.1`, confirmed that training works, and froze the result:

```
pip freeze > requirements.lock
```

```
joblib==1.1.0
numpy==1.23.1
pandas==1.4.3
python-dateutil==2.9.0.post0
pytz==2026.4
PyYAML==6.0.3
scikit-learn==1.1.2
scipy==1.13.1
six==1.17.0
threadpoolctl==3.7.0
```

Ten lines, from four direct requirements. Commit the lock file. Tools such as `pip-tools` and `uv` can generate lock files with dependency resolution; conda users use an `environment.yml` with `conda env export`. We did not run those here, so check their current documentation.

## Prove it: rebuild from scratch

A lock file you have never used is a guess. Create a brand-new environment from it and compare:

```
python -m venv venvB
venvB\Scripts\python -m pip install -r requirements.lock
venvB\Scripts\python -m pip freeze | diff - requirements.lock
```

The diff printed nothing (identical), and `python -m churn.train` returned `trained on 750 rows; {'accuracy': 0.768}`, the same score as before. Do this check in CI later in the course. Also record the Python version itself, for example in the README or a `.python-version` file if you use pyenv, since a lock file cannot enforce it.

## Record the environment with the model

A small helper writes a fingerprint of what actually ran, which you can save next to `metrics.json`:

```python
import json, platform
from importlib.metadata import version

env = {"python": platform.python_version()}
for p in ["numpy", "pandas", "scikit-learn", "joblib"]:
    env[p] = version(p)
print(json.dumps(env, indent=2))
```

It printed Python 3.9.13, numpy 1.23.1, pandas 1.4.3, scikit-learn 1.1.2 and joblib 1.1.0.

## Why the model file cares

A `.joblib` file is a Python pickle. It stores the estimators' attributes, and it expects the same library code to read them. We trained the churn pipeline under scikit-learn 1.1.2, then loaded it in a second environment with scikit-learn 1.6.1. Loading printed `InconsistentVersionWarning: Trying to unpickle estimator Pipeline from version 1.1.2 when using version 1.6.1` for each step, and calling `predict_proba` then failed with `AttributeError: 'SimpleImputer' object has no attribute 'keep_empty_features'`. Loud failures like this are the good outcome; a subtler mismatch could return slightly different predictions without any error. Serve a model with the versions that trained it.

## Recap

An environment is an input to training. Isolate it with a virtual environment, pin direct and transitive dependencies in a lock file, prove the lock by rebuilding from scratch, and save a fingerprint beside each model. Containers extend this to the operating system, which Chapter 3 covers. Next, we tackle the other big input that Git does not hold: the data itself, with data versioning.
