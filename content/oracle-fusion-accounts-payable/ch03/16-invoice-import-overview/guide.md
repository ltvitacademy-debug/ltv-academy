# Invoice Import Overview

Every invoice so far in this course has been entered one at a time, by a person, into the Invoices work area. That's fine for a handful of invoices a day. It falls apart the moment a company receives hundreds of invoices through EDI, a spreadsheet upload, a scanning/OCR tool, or a supplier's own self-service portal submission. This lesson covers how Payables absorbs invoices in bulk, through **import**, rather than one screen at a time.

## What you'll learn

- Where imported invoice data actually lands before it becomes a real invoice
- What the Import Payables Invoices process does
- Common reasons an imported invoice gets rejected instead of created
- Where rejections get reported, and why checking them is part of the job

## Invoices land in an interface table first

Imported invoice data doesn't become a real Payables invoice instantly. It first lands in **open interface tables** — most notably one holding header-level data for every invoice waiting to be imported. Whatever system or process generated the data (a spreadsheet loader, an EDI feed, a scanning tool, a supplier portal submission) writes rows into this staging area, not directly into Payables' own invoice tables.

## The Import Payables Invoices process

The **Import Payables Invoices** process is what actually reads those staged rows and builds real Payables invoices and invoice lines from them — the same kind of invoice you've been creating manually all chapter, just generated by a batch process instead of a person typing into a form. Running this process is a deliberate, scheduled step, not something that happens automatically the instant data lands in the interface table.

## Why some imported invoices get rejected instead of created

Import isn't a guaranteed pass-through. A staged invoice gets **rejected** — left out of the invoices actually created — for reasons that will sound familiar from earlier lessons:

- **No valid supplier site can be identified** — if the import data doesn't resolve cleanly to a real supplier and site, Payables has nowhere to attach the invoice.
- **Duplicate invoice number for the supplier** — the same duplicate-detection control from lesson 13 applies here too; importing "INV-4471" from Vantree twice gets the second one rejected.
- **An invalid or unexpected source value** — the "source" identifies where an imported invoice came from, and if it isn't one of the predefined options (or a properly defined lookup value), the row is rejected rather than guessed at.
- **Conflicting payment terms data** — depending on configuration, supplying payment terms directly in the imported data when the source isn't set up to allow it can also cause a rejection.

## Rejections aren't silent

Every run of the import process generates a rejections report alongside whatever invoices it successfully creates, listing exactly which staged rows failed and why. This matters practically: a batch of 400 imported invoices that successfully creates 395 is not actually "done" until someone checks why the other 5 were rejected and fixes the underlying data (a missing supplier site, a bad source value) before re-attempting them — otherwise those five supplier invoices simply vanish from view instead of getting paid.

## Recap

Imported invoice data lands in open interface tables first, and the Import Payables Invoices process turns valid staged rows into real invoices. Rows get rejected for reasons like an unidentifiable supplier site, a duplicate invoice number, or an invalid source, and every import run produces a rejections report that needs to be checked, not ignored.
