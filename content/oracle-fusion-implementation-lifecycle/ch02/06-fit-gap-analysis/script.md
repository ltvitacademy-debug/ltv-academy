# Script — Fit-Gap Analysis

## Segment 1 (title)

Chapter one ended with a workshop surfacing something that didn't map cleanly onto standard Oracle functionality. Fit-gap analysis is the formal exercise that takes every requirement gathered so far and classifies it: does standard functionality satisfy it as-is, a fit, or is there a gap that needs a decision?

## Segment 2 (steps)

In a fit-gap session, the functional consultant walks through the relevant Oracle Modern Best Practice flow, often in a sandbox, and the process owner answers one question: does this satisfy the requirement? Yes means fit, straight to the configuration workbook. No means gap, and it needs further classification.

## Segment 3 (steps)

Gaps generally fall into three categories. A configuration gap just needs a non-default setup choice, no code. A process gap means the business process itself needs to change, which is often the hardest to close because it needs change management, not configuration. An extension gap genuinely needs a personalization, an integration, or a custom report.

## Segment 4 (steps)

Adopt, not adapt means the team should actively try to resolve a gap toward configuration or process change before accepting an extension, because extensions carry ongoing cost: they have to be re-tested every quarterly update and don't automatically benefit from new Oracle features.

## Segment 5 (outro)

Brightfield's manual wire-matching problem turns out to be mostly a configuration gap once reconciliation matching rules are set up correctly, with one small piece, a legacy report format, becoming a genuine extension gap for the technical consultant.
