# Lesson 29 — Designing an Access Governance Model · Voiceover script

Segments map 1:1 to slides. Target: ~2-3 minutes total.

---

## S1 · TITLE CARD

Chapter 3 covered roles, least privilege, segregation of duties, and
access reviews as separate topics. An access governance model is what
you get when you stop treating them as five separate lessons and
design them as one connected system.

## S2 · STEPS CARD (five building blocks)

Role definitions start from job function, not from copying someone
else's access. Least-privilege mapping scopes each role to the
minimum it actually needs. Segregation-of-duties rules define which
role combinations are never allowed on one person. And a request and
approval workflow, backed by periodic recertification, makes sure
access is granted deliberately and reviewed on a schedule.

## S3 · CODE CARD (a written SoD rule)

Here's a segregation-of-duties rule written down concretely: creating
a vendor and approving vendor payments never combine on one person.
That rule gets checked at request time, before access is granted — and
recertification catches it if the combination ever appears later
anyway.

## S4 · STEPS CARD (mapped to Brightfield)

Brightfield's incident traced to exactly two missing pieces from this
model: no approval workflow requiring a named, scoped justification —
access was granted on an informal ask — and no recertification cadence
that would have caught the still-active login after the contract
ended.
