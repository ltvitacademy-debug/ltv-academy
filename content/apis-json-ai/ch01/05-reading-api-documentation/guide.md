# Lesson 5 — Reading API Documentation

**Chapter 1 · Understanding APIs · Lesson 5 of 22**

## What you'll learn

- The three things to find first in any unfamiliar API's documentation
- How real documentation tools (Swagger/OpenAPI, Postman) display
  methods, endpoints, and parameters
- How to tell a required parameter from an optional one at a glance
- Why documentation conventions repeat across different tools and sites

## Three things to find first

Opened cold, API documentation can look overwhelming. Every good doc
page answers the same three questions, though — find these first and
the rest is detail:

```
1. Base URL & auth   — where do requests go, and how do you prove who you are?
2. Endpoints         — what resources exist, and which methods work on each?
3. Required params   — what must you send, vs. what's optional?
```

## Methods, color-coded

The screenshot below is a real, live documentation page generated by
Swagger UI — one of the most widely used tools for auto-generating docs
directly from an API's OpenAPI specification. Notice each endpoint's
method is color-coded: green for `POST`, orange for `PUT`, blue for
`GET`. That color convention shows up across most API doc tools, not
just this one — it's worth recognizing on sight.

## Required vs. optional, spelled out

Click into an endpoint and real documentation spells out exactly what
each parameter needs. In the second screenshot, the `status` parameter
is marked **required**, typed as `array<string>`, sent as a **query**
parameter, and limited to three allowed values: `available`, `pending`,
`sold`. Missing a required parameter is one of the most common causes of
a `400 Bad Request` — Lesson 3 already taught you what that status code
means.

## The same shape, a different tool

The third screenshot comes from a completely different documentation
site, generated by a different tool — yet it answers the exact same
questions: which headers are required, what type each parameter expects,
and what the valid values are. Once you know what to look for, you can
read almost any API's docs, regardless of which tool generated them.

## From documentation to a real request

```
GET /pet/findByStatus?status=available
Required: status (query, array<string>)
Auth: none for this sample endpoint
```

That's the whole translation: take the documented method, URL, and
required parameters, and build the request Lesson 4 already taught you
the anatomy of.

## Key terms

| Term | Meaning |
|---|---|
| OpenAPI / Swagger | A specification/tool pair for describing and auto-generating API docs |
| Required parameter | Must be sent, or the request fails (often with `400`) |
| Query parameter | A parameter sent in the URL after `?` (Lesson 4) |
| Base URL | The root address every endpoint in the docs is relative to |
