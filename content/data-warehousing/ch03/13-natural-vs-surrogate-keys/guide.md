# Lesson 13 — Natural vs. Surrogate Keys

**Chapter 3 · Dimension Tables · Lesson 13 of 39**

## What you'll learn

- A direct, side-by-side comparison of natural keys and surrogate keys
- Why a dimension table keeps **both**, even though only one is the
  primary key
- The date dimension's deliberate exception to "surrogate keys are
  meaningless"
- How to decide, at design time, which columns get which role

## Two jobs, two keys

Lesson 12 introduced the surrogate key on its own. Side by side, the two
kinds of identifier a dimension table carries look like this:

| | Natural key | Surrogate key |
|---|---|---|
| Origin | The source system | Generated by the warehouse itself |
| Meaning | Business-meaningful (an `EmployeeID`, a `ProductCode`) | Meaningless — just an integer |
| Uniqueness | Not guaranteed to stay unique over time | Always unique — it's the primary key |
| Used for | Tracing a row back to its source | Joining fact tables, tracking history |

Neither key is optional. A well-designed dimension table keeps **both** —
the natural key so you can always trace a row back to where it came
from, and the surrogate key as the actual primary key everything else
joins against.

## Why keep the natural key at all, if it's not the primary key?

If the surrogate key does all the real work, it's tempting to drop the
natural key entirely. Don't — you lose two things if you do:

- **Traceability.** When a number looks wrong in a report, you need to
  trace the warehouse row back to the exact source-system record it came
  from. Without the natural key sitting right there on the row, that
  becomes a much harder investigation.
- **Change detection.** The ETL process that loads a dimension table
  (Chapter 5 covers staging and loading in depth) has to compare
  incoming source rows against what's already in the warehouse — and it
  does that comparison using the natural key, because the surrogate key
  doesn't exist yet for a row that hasn't been loaded.

## The exception: date and time dimensions

Every rule in this course about surrogate keys being meaningless has one
accepted exception: **date and time dimensions**. A date dimension's
surrogate key is conventionally stored as an `INT` in `YYYYMMDD` format
— `20260911` for September 11, 2026 — while its natural key uses SQL
Server's actual `DATE` data type. This is deliberate:

- It's human-readable, which makes debugging and ad-hoc querying easier
- It sorts correctly as a plain integer, with no extra logic needed
- It follows the unambiguous ISO 8601 date convention

A time dimension follows the same idea at a finer grain — `HHMM` or
`HHMMSS` as the surrogate key format.

## Deciding which is which, at design time

When you're designing a new dimension, ask: does this identifier come
from a source system, or does the warehouse invent it? If it comes from
a source system, it's a natural key candidate — but the primary key on
the dimension table itself should still almost always be a fresh
surrogate key, except for that one date/time exception above.

## Key terms

| Term | Meaning |
|---|---|
| Natural key | The source system's own identifier — kept for traceability and change detection |
| Surrogate key | The warehouse's own generated identifier — always the primary key |
| ISO 8601 | The international date format standard (`YYYYMMDD`) the date dimension's surrogate key follows |
