# Lesson 9 — Issue Management and Escalation

**Chapter 2 · Policies, Standards and Processes · Lesson 9 of 25**

## What you'll learn

- What belongs in an issue log, and why "we'll remember" isn't a tracking system
- How to assign severity levels that actually drive urgency, not just a label
- A practical escalation ladder built on Chapter 1's roles
- Why not every issue should escalate, and what happens when escalation becomes the default

## Why an issue log, not memory

Lesson 8's workflows described resolution and closure as stages — but at any given moment, a
governance program has multiple issues open at once, at different stages, owned by different
stewards. An **issue log** is the single record of all of them: what's open, who owns each one,
how severe it is, and how long it's been sitting. Without one, the program has no way to answer
"how are we actually doing" except by asking around — and issues that nobody's actively chasing
quietly die in someone's inbox.

## What belongs in an issue log

| Field | Purpose |
|---|---|
| Issue ID | Unique, trackable reference |
| Description | What's actually wrong, in plain language |
| Domain | Which data domain and which owner/steward it falls under |
| Severity | How urgent — see the levels below |
| Status | Open, in progress, escalated, resolved, closed |
| Opened / due date | When it was raised, and when it's expected to be handled by |

## Assigning severity that actually drives urgency

A severity label only matters if it changes behavior. A practical four-level scale:

1. **Critical** — actively causing harm right now (a regulatory violation in progress, a wrong
   number driving a live business decision) — same-day attention
2. **High** — a known problem with real business impact, not yet causing active harm — days, not
   weeks
3. **Medium** — a real quality or process gap worth fixing — weeks, on a normal backlog cadence
4. **Low** — a minor inconsistency or nice-to-have — addressed when capacity allows

If "critical" and "medium" issues get the same response time in practice, the severity field is
decorative, not functional.

## A practical escalation ladder

Escalation uses the same roles Chapter 1 built, in order:

1. **Steward** — first line; resolves what's within their domain and authority
2. **Data owner** — steps in when the issue crosses what the steward alone can decide, or needs
   business-context judgment
3. **Governance committee** — handles cross-domain disputes or issues that need policy-level
   authority (Lesson 3's structure)
4. **Sponsor / council** — the last resort, for anything with organization-wide stakes or a
   resourcing fight the committee can't settle alone

An issue escalates when it crosses a domain boundary, breaches its severity's expected response
time, or needs authority the current holder doesn't have — not simply because it's taking a while.

## Why escalating everything is its own failure

An escalation path only works if it's used selectively. A program where every minor issue gets
pushed straight to the sponsor trains the organization to ignore escalations — the signal gets
buried in noise, and when something genuinely needs the sponsor's attention, it looks like business
as usual. Escalation is for issues that are actually stuck at the current level, not a way to avoid
owning a decision.

## Key terms

| Term | Meaning |
|---|---|
| Issue log | The documented record of every open governance issue, its severity, owner, and status |
| Severity level | A classification (critical/high/medium/low) that drives expected response time |
| Escalation ladder | The ordered path (steward → owner → committee → sponsor/council) an issue moves up when it's genuinely stuck |
