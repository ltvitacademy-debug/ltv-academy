## What a SAS token is

A **SAS token** is a signed set of query-string parameters appended to a
storage URI, granting **time-limited, scoped access** — to one blob, one
container, or a whole account — without sharing an account key and
without creating any kind of identity at all:

![A real SAS URI broken into three labeled parts: the storage resource URI, a question-mark delimiter character, and the SAS token itself as a query string with parameters like sv, sr, sig, and sp.](/courses/de-foundations/ch01/07-sas-tokens/sas-storage-uri.png)
*Everything after the `?` is the SAS token — a signature plus a set of parameters describing exactly what it allows.*

Reading a few of those real parameters: `sv` is the signed API version,
`sr` is the signed resource type (`b` for blob), `sp` is signed
permissions (read, write, delete...), and `sig` is the actual
cryptographic signature proving the token was generated by someone who
had the account key — without that signature ever being exposed itself.

## The pattern SAS tokens exist for

The classic use case: a client application needs to upload or download a
file directly to storage, but you don't want to route all of that file
traffic through your own backend:

![A diagram showing a laptop client uploading/downloading data to and from a Front End Proxy Service, which in turn saves/reads data to Microsoft Azure Storage.](/courses/de-foundations/ch01/07-sas-tokens/sas-storage-fe-proxy-service.png)
*The backend issues a short-lived SAS token, then gets out of the way — the client uploads or downloads directly against storage.*

Your backend authenticates the user, decides they're allowed to upload
one specific file, generates a SAS token scoped to exactly that, and
hands it to the client. The client then talks **directly** to Azure
Storage using that token — your backend never has to proxy the actual
file bytes.

## SAS tokens vs. managed identities

Both grant access without a stored account key, but for different
situations:

- **Managed identity** (Lesson 6): for a resource **you control** —
  a Function App, a VM, a Databricks cluster — that needs standing,
  ongoing access.
- **SAS token**: for a client you *don't* fully control, or access that
  should genuinely expire — a browser upload, a link shared with an
  external partner, a mobile app.

## Why the expiry matters most

Every SAS token has a signed expiry time. Because the permissions and
expiry are baked into the signed token itself, revoking access early
(before it naturally expires) generally requires rotating the underlying
account key — which invalidates *every* SAS token signed with it. This is
exactly why real systems generate SAS tokens with the shortest expiry
that's actually practical, not "just in case" long-lived ones.

## Key terms

| Term | Meaning |
|---|---|
| SAS token | A signed, time-limited, scoped set of permissions appended to a storage URI |
| sv / sr / sp / sig | Signed version, resource type, permissions, and signature — the core SAS query parameters |
| Front end proxy pattern | Backend issues the SAS token; the client talks directly to storage afterward |

## Lab

In the Azure Portal, on a storage account:

1. Open **Shared access signature** (left navigation, under **Security +
   networking**).
2. Set a short expiry (e.g., 1 hour) and limited permissions (Read
   only), then generate a SAS token.
3. Paste the generated URI into your browser's address bar — note that
   the `sig` parameter is what's actually proving you're authorized.
