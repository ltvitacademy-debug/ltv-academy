## The purpose: handle the asks that work as designed

ITIL 4 defines the purpose of service request management as supporting
the agreed quality of a service by handling all predefined,
user-initiated service requests in an effective and user-friendly
manner. Notice what's absent from that sentence: nothing is broken.
A **service request** is a formal ask from a user for something to
happen — provision a new laptop, grant access to a shared drive, reset
a password, order a software license, answer a how-do-I question. The
service is working exactly as designed; the user just needs the
provider to do one of the things it's designed to do. That is the
clean line between this practice and incident management: an incident
is an unplanned interruption, while a service request is a planned,
expected, routine ask.

## Why "predefined" is the whole idea

The word "predefined" in the purpose statement is doing real work.
Service request management is not meant for open-ended, one-off
problem-solving — it's built around requests that have already been
thought through in advance: what information is needed, who has to
approve it, what steps fulfill it, and how long it should take. A
request for a new laptop doesn't need someone improvising a process
every time; it needs a known workflow that already specifies the
approval chain and the fulfillment steps. Standardizing requests ahead
of time is what makes this practice fast and consistent instead of
reinventing the wheel on every ticket.

## The service catalog as the front door

The usual mechanism for surfacing predefined requests to users is a
**service catalog** (or request catalog): a menu of exactly what can
be asked for, with the information needed up front, so neither the
user nor the fulfiller has to guess. Clicking "Request new laptop"
from a catalog captures the model, the cost center, and the approver
in one step, instead of a vague email that someone has to interpret.
Many requests in the catalog carry **approval steps** — a manager
signing off on a software purchase, security approving elevated access
— built into the workflow itself rather than handled as a side
conversation. Some requests skip approval entirely and fulfill
automatically or near-instantly, like a password reset or an
information request, because the risk is low enough that pre-approval
was already baked into the design.

## Key terms

| Term | Meaning |
|---|---|
| Service request | A predefined, user-initiated request for something the service already does by design |
| Service catalog | A menu of requests users can make, with required information captured up front |
| Predefined request | A request whose approval chain and fulfillment steps were designed in advance, not improvised |
| Approval workflow | A built-in sign-off step (e.g., a manager or security approver) attached to certain catalog requests |
