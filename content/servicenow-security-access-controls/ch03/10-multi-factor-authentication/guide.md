## A password is "something you know" — and that's the whole problem

Every password, no matter how strong, is a single piece of
information: something the user knows. The trouble is that "something
you know" can be stolen without the user doing anything wrong at all
— a phishing email that harvests it, a data breach at some unrelated
site where the same password got reused, a keylogger on a compromised
machine. Once an attacker has that one piece of information, a
password-only system has nothing left standing in their way. They
type it in, and they're in.

Multi-Factor Authentication closes that gap by requiring a second,
*independent* proof of identity — something that category of attack
doesn't also hand over. The two common real-world examples are a
one-time code generated by an authenticator app on the user's phone,
and a push notification sent to a trusted device that the user has
to approve. Both depend on the user physically possessing a specific
device, which is a fundamentally different kind of proof than "knows
a string of characters."

```
Password alone:                    Password + MFA:
"something you know"                "something you know"
  -- stealable via phishing,          PLUS
     breach, or keylogger            "something you have"
                                       -- a device, a one-time code
A stolen password = full access.    A stolen password alone = nothing.
                                     The attacker still needs the device.
```

## The real benefit, stated precisely

MFA doesn't make passwords unstealable — phishing still works exactly
as well as it ever did at getting someone to type their password into
a fake page. What MFA changes is what that stolen password is worth
to the attacker afterward. Without the second factor, a stolen
password alone is immediately sufficient to log in. With MFA in
place, a stolen password alone accomplishes nothing — the attacker
also needs the one-time code or the push approval, which they
typically don't have. That's the specific, concrete reason MFA is
considered one of the single highest-value security controls an
organization can add: it doesn't prevent credential theft, it defeats
it after the fact.

## Where MFA actually gets enforced in practice

Here's the part that connects directly back to Lesson 9. Most
organizations do **not** configure MFA natively inside ServiceNow
itself. Instead, they enforce it at the Identity Provider — the same
IdP from the SAML flow that already sits at the enterprise's one
authentication chokepoint. That's a deliberate, sensible choice, not
an oversight: the IdP is already the single point where every
connected application's login flows through, so enforcing MFA there
means it applies consistently across the entire application
portfolio — ServiceNow included — rather than needing to be
separately configured, application by application, the same scaling
problem Lesson 8 described for password policy.

Mapped onto the seven-step SAML flow from Lesson 9, MFA simply
inserts itself into Step 3 — "user authenticates at the IdP." The IdP
now requires the password *and* the second factor before it will
issue the signed assertion ServiceNow is waiting for in Step 6.
ServiceNow's role in the flow doesn't change at all; it still only
ever receives and verifies a signed assertion.

## What to check when MFA causes a problem

Because enforcement typically lives at the IdP, an MFA login failure
is usually an IdP-side issue — a lost or unenrolled device, an
expired one-time code, a push notification the user never approved
in time — not a ServiceNow configuration problem. Confirming where
the failure actually occurred (at the IdP's challenge, versus
ServiceNow's assertion validation) is the first diagnostic step,
echoing the same "classify before you touch anything" discipline from
the ACL Lab.

## Key terms

| Term | Meaning |
|---|---|
| Multi-Factor Authentication (MFA) | Requiring a second, independent proof of identity beyond a password |
| Something you know / something you have | The two different categories of proof MFA combines |
| One-time code / push approval | The two common real-world second factors |
| IdP-enforced MFA | The typical enterprise pattern — MFA configured at the Identity Provider, not natively in ServiceNow |
