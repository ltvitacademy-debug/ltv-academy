# Image Tagging & Versioning

Lesson 16 pushed `northbridgeretail/catalog:1.4` with barely a second thought about what `1.4` meant. A real deployment pipeline tags more deliberately — one image, several tags, each one answering a different question: "what version is this," "what's the latest build," and "exactly which commit produced this."

## What you'll learn

- How one image can carry multiple tags at once
- Three tagging conventions and what each one is actually for: semantic versions, `latest`, and git-sha
- Why overwriting a tag that's already in production is dangerous
- How to apply several tags to the same build in one pipeline run

## One image, several tags

`docker tag` doesn't move or copy image data — it just points a new name at an image ID that already exists locally:

```text
$ docker build -t northbridgeretail/catalog:1.5 .
$ docker tag northbridgeretail/catalog:1.5 northbridgeretail/catalog:latest
$ docker tag northbridgeretail/catalog:1.5 northbridgeretail/catalog:a1b2c3d

$ docker push northbridgeretail/catalog:1.5
$ docker push northbridgeretail/catalog:latest
$ docker push northbridgeretail/catalog:a1b2c3d
```

All three tags — `1.5`, `latest`, and `a1b2c3d` — point at the exact same image ID. Pulling any of them downloads identical bytes.

## Three conventions, three jobs

- **Semantic version** (`1.5`, `2.0.1`) — a human-meaningful release number Northbridge bumps deliberately, following semver: major changes break compatibility, minor adds features, patch fixes bugs.
- **`latest`** — a convenience pointer to whatever was most recently pushed without an explicit tag. Fine for local development (`docker pull northbridgeretail/catalog` with no tag defaults to it); never safe to deploy by, because "latest" silently means something different every day.
- **Git SHA** (`a1b2c3d`) — the exact commit that produced the build, generated automatically by CI. Unambiguous and traceable straight back to source code, at the cost of being meaningless to a human reading it alone.

## Why tags shouldn't be overwritten once deployed

A tag is just a label — nothing stops `docker push` from repointing `northbridgeretail/catalog:1.5` at a completely different image tomorrow. That's exactly the problem: if production is running `catalog:1.5` and someone re-pushes a different build under that same tag, every container that later pulls `1.5` — restarts, autoscaling, a new server — gets different code with no warning.

Northbridge's rule: **once a semver or git-sha tag is pushed to production, it's immutable.** Fixing a bug means cutting `1.5.1`, not re-pushing `1.5`. `latest` is the one tag that's allowed to move, precisely because nothing in production is ever deployed by `latest` alone.

```text
$ docker pull northbridgeretail/catalog:a1b2c3d
a1b2c3d: Pulling from northbridgeretail/catalog
Status: Downloaded newer image for northbridgeretail/catalog:a1b2c3d
```

That pull will return the exact same bytes a year from now as it does today — the whole point of pinning a deploy to a git-sha tag instead of `latest`.

## Key terms

- **Tag** — a human-readable label pointing at a specific image ID; one image can have many tags
- **Semantic versioning (semver)** — `MAJOR.MINOR.PATCH` version numbers bumped deliberately on release
- **`latest`** — the default tag applied to an image pushed without an explicit one; safe for development, unsafe for deploys
- **Git-SHA tag** — a tag named after the exact commit hash that produced the build, generated by CI
- **Immutable tag** — a tag that, once pushed to production, is never repointed at a different image
