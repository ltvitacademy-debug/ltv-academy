# Script — Course Introduction: From Relational to NoSQL Thinking

## Segment 1 (title)

Every course in this path so far has been about relational databases — different engines, same underlying model. This final course asks you to set that model down. MongoDB, Cosmos DB, and Neo4j each organize data in a genuinely different shape.

## Segment 2 (code: not a lesser version of relational)

It's tempting to treat NoSQL as relational-minus-constraints. That's wrong. A document database isn't relational data with the joins removed — it's built around denormalizing data to match how an application actually reads it. A graph database isn't a table with extra steps — relationships are first-class, stored objects.

## Segment 3 (steps: three platforms, three real reasons)

MongoDB, the most widely adopted document database. Azure Cosmos DB, Microsoft's globally-distributed multi-model service — the natural next step after this catalog's Azure DBA content. And Neo4j, the leading graph database, for problems that are genuinely awkward to model relationally.

## Segment 4 (outro)

NoSQL modeling starts from the opposite direction of relational design — understand the access pattern first, then shape the data to match it. Next up: the CAP theorem and the real tradeoffs behind that shift.
