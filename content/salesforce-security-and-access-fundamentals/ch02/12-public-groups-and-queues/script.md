# Script — Public Groups and Queues

## Segment 1 (title)

Sharing rules always share to a public group or a role, never an individual. This lesson covers the two reusable containers behind almost everything else in this chapter — public groups and queues.

## Segment 2 (screenshot: New Public Group)

A public group is a named, reusable bundle of members, built once and referenced by as many sharing rules or report folders as needed. It isn't limited to individual users either — a group can contain users, roles, roles and subordinates, even other public groups, nested arbitrarily.

## Segment 3 (screenshot: Queues list)

A queue looks similar on the surface, but it solves a different problem — it's a holding location for unassigned records. Cases or leads route into a queue, manually or by assignment rule, and sit there until a member accepts one to work it.

## Segment 4 (screenshot: Queue Members)

Adding members to a queue uses the exact same picker pattern you've seen throughout this chapter — search by user, role, or group, move them into Selected Members. Familiar mechanics, different purpose underneath.

## Segment 5 (steps: visibility vs distribution)

Public groups answer who should be able to see something. Queues answer who's responsible for working it, and how it gets assigned. A support team often uses both on the same object — a group for broad visibility into escalated cases, a queue to actually route unworked ones to whoever claims them next.
