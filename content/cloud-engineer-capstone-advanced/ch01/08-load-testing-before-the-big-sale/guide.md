## Designing the test

With the sale under two weeks out, Theo runs a load test against `checkout-api` through the real
Ingress endpoint, using k6 from a single Azure DevOps Microsoft-hosted pipeline agent in East US:

```javascript
import http from "k6/http";
import { check, sleep } from "k6";

export const options = {
  stages: [
    { duration: "2m", target: 100 },
    { duration: "5m", target: 500 },
    { duration: "3m", target: 500 },
    { duration: "2m", target: 0 },
  ],
  thresholds: {
    http_req_duration: ["p(95)<300"],
    http_req_failed: ["rate<0.01"],
  },
};

export default function () {
  const res = http.post(
    "https://shop.driftwoodapparel.com/api/checkout/session",
    JSON.stringify({ cartId: `cart-${__VU}-${__ITER}` }),
    { headers: { "Content-Type": "application/json" } }
  );
  check(res, { "status is 200": (r) => r.status === 200 });
  sleep(1);
}
```

This is a genuinely reasonable test design: it ramps virtual users from 0 to 500 over several
minutes, holds peak load, and checks real SLO thresholds — p95 latency under 300ms, error rate
under 1%. Nothing about writing it this way is careless.

## The results

```
checkout_latency_p95.............: 214ms
http_req_failed...................: 0.21%
checks.............................: 99.79% ✓ 4982   ✗ 11

 ✓ http_req_duration..............: p(95)<300
 ✓ http_req_failed................: rate<0.01
```

Both thresholds pass comfortably. `checkout-api`'s HPA scales from 6 replicas to 18 during peak
load, Container Insights shows cluster-wide CPU holding around 52%, and the FinOps dashboard from
Lesson 7 shows nothing unusual. By every number this test reports, the platform is ready.

## What this test's traffic pattern doesn't do

Here's the detail worth sitting with, because it's the real reason this test passes cleanly
without catching the gap from Lesson 4: k6's 500 virtual users all originate from **one pipeline
agent, in one Azure region**, each one simply looping the same request as fast as its think-time
allows. That's standard, reasonable synthetic load — it's exactly how most pre-launch load tests
are built, and it correctly exercises `checkout-api`'s CPU, memory, and HPA scaling behavior under
volume.

What it does *not* reproduce is the specific scheduling pattern real sale traffic will cause: a
rapid, bursty scale-out — the HPA adding several new pods within a single short window, repeatedly,
as real shopper traffic surges unevenly rather than ramping smoothly — which is exactly the
condition under which the Kubernetes scheduler's pod-placement decisions (absent the
`topologySpreadConstraints` missing since Lesson 4) are most likely to concentrate new pods onto
whichever nodes and zones happen to have room *at that exact moment*, rather than spreading evenly.
A smooth, single-origin synthetic ramp scales `checkout-api` out gradually and gives the scheduler
time to place pods onto a wide, evenly available set of nodes — it simply never creates the kind
of sudden, uneven scheduling pressure that a real, bursty holiday sale will.

## Why "the test passed" is true, and also not the whole answer

Nothing in this lesson invalidates the load test. It answered exactly the question it was built to
answer: does `checkout-api` meet its latency and error-rate SLOs under 500 concurrent users' worth
of volume? Yes, cleanly. The test was never designed to answer a second, different question — does
pod placement hold up evenly across availability zones under a bursty, multi-origin scale-out
event — because nobody had identified that as a distinct risk serious enough to test for
separately. That's not a process failure so much as a gap in what "load testing" was scoped to
mean going into the sale. The sale itself, starting in Lesson 9, is the first time that second
question gets asked at all.

## Key terms

| Term | Meaning |
|---|---|
| SLO (Service Level Objective) | A measurable target for a service's behavior (like p95 latency under 300ms) that a test or production metric is checked against |
| Synthetic traffic | Load generated by a test tool rather than real users, used to approximate real-world volume and patterns |
| Single-origin load test | A test where all simulated traffic originates from one client or region, as opposed to many real, geographically distributed users |
| Bursty scale-out | A rapid, uneven spike in replica count driven by a sudden traffic surge, as opposed to a smooth, gradual ramp |
