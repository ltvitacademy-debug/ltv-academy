# Dashboard Design Best Practices

**Chapter 3 · Dashboards · Lesson 18 of 22**

Every tool from this chapter — widgets, filters, dynamic running users — can build a technically correct dashboard that's still useless, because nobody can tell what it's trying to say at a glance. This lesson closes the chapter with the habits that separate a dashboard people actually open every morning from one they learn to ignore.

## What you'll learn

- Leading with what matters most, above the fold
- Choosing restraint over completeness
- Consistency across widgets and dashboards
- Naming and grouping that make a dashboard self-explanatory
- A short pre-publish checklist

## Lead with what matters most

The first screen — what's visible before any scrolling — should answer the single most important question the dashboard exists to answer. A well-organized dashboard puts key totals (pipeline, win rate, top accounts) up top and supporting detail below, not the other way around. If a viewer has to scroll to find the one number they open the dashboard for, the layout has already failed.

## Restraint beats completeness

A dashboard trying to show everything shows nothing clearly. Every widget added is one more thing competing for attention — pick the handful of numbers that actually drive a decision, and leave the rest to the underlying reports someone can click into. "View Report" links under each widget exist precisely so a dashboard doesn't have to cram in every possible detail.

## Consistency, across widgets and across dashboards

Use the same chart type for the same kind of question everywhere — don't make one trend a line chart and an identical trend elsewhere a bar chart. Keep color meaning consistent (if blue means "this quarter" on one widget, it should mean that everywhere on the same dashboard). Reused patterns mean a viewer who's learned to read one dashboard in the org can read the next one just as fast.

## Naming and grouping

Widget titles should describe the number, not just repeat the report name — "Open Pipe This FQ" tells a viewer something; "Report 3" doesn't. Group related widgets together spatially (all pipeline widgets near each other, all activity widgets near each other) so the eye doesn't have to hunt across the grid to compare related numbers.

## A short pre-publish checklist

- Does the most important number show up without scrolling?
- Could any widget be cut without losing anything a viewer actually needs?
- Would a first-time viewer understand each widget's title without opening it?
- Is the chart type right for the question each widget answers (Lesson 15)?
- Is the dashboard in the right folder, shared with the right audience (Lesson 10)?

## Recap

- Put the most important number above the fold — don't make anyone scroll for it.
- Fewer, well-chosen widgets beat a dashboard trying to show everything.
- Keep chart types and color meaning consistent across widgets and dashboards.
- Name widgets for what they tell a viewer, not just the report behind them.

## Check yourself

A dashboard has twelve widgets, no two using the same chart type for similar data, and the most important number is the eighth thing a viewer sees. What two design habits from this lesson does it violate, and which would you fix first?
