# Lesson 10 — Writing a ServiceNow Resume

**Chapter 3 · Building a ServiceNow Portfolio · Lesson 10 of 26**

## What you'll learn

- Why a vague professional summary loses to a specific skills line, every time, for a ServiceNow-track resume
- How to turn the six artifacts from Lesson 9 into resume bullets that name real modules, real scripting, and real integration patterns
- The honest way to quantify impact when you don't have real production metrics to cite
- How to list an in-progress certification without implying it's already earned

## Lead with specifics, not summary language

A line like "results-driven IT professional with strong technical skills and a passion for problem-solving" tells a recruiter nothing a ServiceNow applicant tracking system can match against a requisition. What a ServiceNow-track resume needs instead is specific platform vocabulary, right at the top: which modules you've configured (Incident, Problem, Change, Service Catalog), which scripting constructs you can write (Business Rules, Client Scripts, Script Includes, Scheduled Jobs), and which integration tools you've used (IntegrationHub, REST/SOAP APIs, Flow Designer). A recruiter or hiring manager scanning dozens of resumes a day, and the keyword-matching system behind many applicant tracking tools, both respond to named platform capabilities far more reliably than to adjectives. "Configured Incident and Change management workflows; built a four-step approval flow in Flow Designer; wrote Script Includes to extend a scoped application's server-side logic" does more work in three lines than a paragraph of summary language does in ten.

## Turning Lesson 9's artifacts into resume bullets

Each of the six artifacts from Lesson 9 translates into a bullet built the same way: what you built, which ServiceNow capability it demonstrates, and — where you can honestly do so — what changed as a result. For example: "Built a multi-step Flow Designer automation with conditional branching and approvals, replacing a manual, multi-step ticket-routing process." That's a specific, defensible claim about *what changed structurally* — a manual process became an automated one — without requiring a number you can't support. Compare that to "built a scoped application using Business Rules and Script Includes to extend out-of-box CMDB functionality" for the courses 5-6 artifact, or "designed a CMDB data model aligned to ServiceNow's Common Service Data Model (CSDM)" for the course 9 artifact. Each bullet names the artifact, the specific capability used, and the outcome in concrete, structural terms.

## Quantifying impact honestly

It's tempting to reach for a number — "reduced ticket resolution time by 40%" sounds impressive on a resume. The problem is that these are course lab and capstone projects on a Personal Developer Instance with no real user population and no real baseline to measure against, so a specific percentage like that is not a number you can actually back up, and a good interviewer will ask how you measured it. The honest kind of claim is a **structural** one: "reduced manual ticket-routing steps by automating approval and assignment logic in Flow Designer" is true, specific, and defensible — it describes what changed about the process, not an invented metric about its magnitude. If you later take a real job and genuinely do measure a percentage improvement with real data, that's the time to use a percentage. Until then, structural claims about what you built and what it replaced are both honest and still genuinely compelling to read.

## Listing certifications in progress, honestly

If you're partway through CSA, CAD, or a CIS track when you start applying, list it — just list it accurately. "ServiceNow Certified System Administrator (CSA) — in progress, exam scheduled [date]" or "— in progress" tells a recruiter exactly where you stand. Listing it as simply "ServiceNow Certified System Administrator" with no qualifier, when you haven't actually passed the exam, is the kind of claim that gets caught the moment someone asks to see the certificate or checks ServiceNow's own certification verification tool — and it costs you more credibility than not having the certification yet ever would.

## Key terms

| Term | Meaning |
|---|---|
| Applicant tracking system (ATS) | Software that scans resumes for keywords matching a job requisition before a human reads them |
| Structural claim | A specific, honest statement about what changed (e.g., manual to automated) without an unverifiable number |
| In-progress certification | A certification you're actively pursuing but haven't yet passed — must be labeled as such, not implied as earned |
| Resume bullet | A single line translating one artifact into capability + outcome, built from real project work |

Pick one artifact from Lesson 9. Write a single resume bullet for it that names the specific ServiceNow capability used and describes the outcome in structural terms, with no invented percentage. Could you defend every word of that bullet if an interviewer asked you to walk through exactly how you built it?
