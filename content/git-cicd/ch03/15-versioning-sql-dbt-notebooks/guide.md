# Lesson 15 — Versioning SQL, dbt Projects & Notebooks

**Chapter 3 · Git for Data Projects Specifically · Lesson 15 of 25**

## What you'll learn

- Pulling Lessons 12-14 together into one real, working project layout
- What actually belongs in Git for a dbt project, and what doesn't
- Versioning raw `.sql` files outside of dbt the same way
- A sanity check for whether a data repository is set up correctly

## A real dbt project's file tree

A dbt project committed correctly looks like this:

```
my-analytics/
├── .gitignore
├── .gitattributes
├── dbt_project.yml
├── packages.yml
├── models/
│   ├── staging/
│   │   └── stg_orders.sql
│   └── marts/
│       └── fct_orders.sql
├── tests/
├── macros/
├── target/            <- ignored, regenerated every run
├── dbt_packages/      <- ignored, regenerated by `dbt deps`
└── logs/              <- ignored, regenerated every run
```

Everything under `models/`, `tests/`, and `macros/` is hand-written
source — it belongs in Git, tracked normally, no different from any
other code. `target/`, `dbt_packages/`, and `logs/` are all
**regenerated automatically** every time dbt runs; committing them
creates merge conflicts on files nobody hand-edits and adds nothing
useful to history.

## The .gitignore that makes this work

```
target/
dbt_packages/
logs/
.env
*.duckdb
```

This is Lesson 12's lesson applied specifically to dbt: ignore
generated output, ignore credentials, ignore local scratch databases.
Nothing here is dbt-specific magic — it's the same reasoning applied
to a real, common project shape.

## Notebooks alongside a dbt project

A repository that mixes exploratory notebooks with a dbt project
applies Lesson 13's guidance directly: `.ipynb_checkpoints/` in
`.gitignore`, cleared outputs before committing, and `nbdime`
configured if the team does serious notebook review. Keep notebooks in
their own top-level folder (`notebooks/`) rather than scattered
throughout `models/` — it keeps the separation between "exploration"
and "production dbt models" visually obvious in the file tree itself.

## Raw SQL files outside of dbt

Not every SQL script lives in a dbt project — ad hoc analysis queries,
one-off migration scripts, and reporting queries for a BI tool often
sit in a plain folder of `.sql` files. These version exactly like any
other text file — no special handling needed, since SQL is plain text
Git diffs perfectly well on its own. The only decision worth making
deliberately: organize them by purpose (`analysis/`, `migrations/`,
`reports/`), the same way you'd organize any other code, rather than
one flat folder of hundreds of undifferentiated `.sql` files.

## A quick sanity check

Before committing to a real data repository, confirm:

- [ ] `target/`, `dbt_packages/`, and `logs/` are in `.gitignore`, not
      in the repository
- [ ] `.env` and any credential file is in `.gitignore`
- [ ] Large reference datasets are either genuinely small, tracked
      with Git LFS, or live in an object store instead
- [ ] Notebooks have cleared outputs, or the team has `nbdime`
      configured

## Key terms

| Term | Meaning |
|---|---|
| `dbt_project.yml` | dbt's project configuration file — always belongs in Git |
| `target/` | dbt's compiled-output directory — never belongs in Git |
| `models/` | Hand-written SQL transformation logic — always belongs in Git |
| `notebooks/` | A dedicated top-level folder keeping exploration visually separate from production models |

## Lab

1. Take a real dbt project (or set one up with `dbt init`) and confirm
   its `.gitignore` matches the pattern in this lesson.
2. If the project has any notebooks, move them into a dedicated
   `notebooks/` folder if they aren't already there.
3. Run through the sanity checklist above against a real repository
   you maintain, and fix anything that doesn't pass.
